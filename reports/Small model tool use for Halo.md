# Fix retries and verified data first

Gemma 4 E2B's failures in Halo are semantic, not structural: in Halo's own untrained first-move test on the 86-task exam, **100% of its 66 tool calls had schema-valid inputs**, yet it made **34.9% wrong first moves** and **announced an action without calling a tool 11.6% of the time**. That points away from constrained decoding and toward three levers: a single validator-guided retry for the announce and wrong-tool cases, supervised fine-tuning (LoRA SFT) on Halo's existing verified step-level trajectories, and an eval that is site-disjoint and repeated. The literature supports SFT on verified data as the most consistent small-model win, and it warns that hard schema decoding can cut semantic accuracy: in one study, a calendar task fell from **91.5% to 48.0% executable accuracy** when a hard tool-call schema replaced prompt-only JSON ([The Constraint Tax, arXiv 2605.26128](https://arxiv.org/abs/2605.26128)). DPO alone degrades small tool-callers, and GRPO has no head-to-head evidence at 2B on a 16 GB Mac. The cloud partner should act as a planner that sees only sanitized sub-questions, with redaction done by deterministic code rather than by the model. One caveat governs every comparison: Gemma's 48.8% first-move rate and ChatGPT's roughly 75% outcome-scored baseline measure different things, so Halo needs an end-to-end Gemma run through the full loop before it can say how far behind it is.

## Measure the failure mix before choosing a fix

Halo's first-move numbers show where the fixes should go. Gemma E2B was right on 54.1% of familiar sites but only 36.0% of the 25 held-out sites, an **18-point gap** that says the model leans on site-specific patterns. Qwen3.5-2B was weaker overall (38.4% right; 20.0% on new sites) and produced more wrong-but-valid calls (47.7%). The 11.6% announce rate for Gemma and 4.7% look-first rate are separate failure types, and each needs its own counter. Any fix should be scored against these buckets, not only against the headline number.

Eval noise matters at this size. With 86 tasks and one run, a proportion near 50% carries a standard error of about **5.4 points** (my arithmetic, sqrt(p(1-p)/n)), so a 10-point gap between models is not decisive on one pass. [tau-bench](https://arxiv.org/pdf/2406.12045) defines pass^k, the chance that all k trials succeed, and shows reliability falling sharply with k; a [Sierra blog summary](https://sierra.ai/blog/benchmarking-ai-agents) reports GPT-4o agents dropping to about 25% at pass^8 on tau-retail (secondary figure). [ReliabilityBench](https://arxiv.org/pdf/2601.06112) warns that pass^k = (pass^1)^k holds only under independence, so Halo should report the per-task success distribution across 3 to 5 runs rather than rely on the formula. Grading also needs to read machine state, not the agent's words. In a [9,876-trajectory study of tau2-bench](https://arxiv.org/pdf/2606.09863), false success accounted for **45-48% of failures** in airline and retail, and no LLM judge exceeded **AUROC 0.65**, while TF-IDF detectors reached 0.83 on task-disjoint splits. Halo's exam should therefore check state after each run, and it should count "claimed done but state wrong" as its own failure class. [AgentRewardBench](https://arxiv.org/abs/2504.08942) found no single judge best across benchmarks, and [Gaming the Judge](https://arxiv.org/html/2601.14691v2) showed chain-of-thought can inflate judged success by about 20 points. Contamination is the other trap: auto-collected training examples must exclude the held-out site URLs and task text, a point [AI Agents That Matter](https://arxiv.org/pdf/2407.01502) makes about benchmark holdouts generally.

## Fine-tuning gives the largest lift, and DPO and GRPO wait

SFT with LoRA is the best-supported technique. A [controlled study of six Qwen3 models from 0.6B to 32B](https://neurips.cc/virtual/2026/172354) found LoRA SFT best in 15 of 18 in-distribution settings and better than full fine-tuning at preserving pretrained agentic behavior. [TinyAgent](https://arxiv.org/html/2409.00608v1) reports fine-tuning lifting its 1.1B model from 12.71% to 78.89% function-calling success on the authors' benchmark, which is the strongest same-model gain found, though it is author-reported and tuned to that benchmark's APIs. [APIGen](https://arxiv.org/pdf/2406.18518) showed that execution and multi-stage verification of synthetic calls gave over 95% correct on a 600-sample human review. Halo's collector already keeps only verified successes and its exporter emits one example per assistant step, which matches the first-move metric directly. That is a real advantage. Negative examples (irrelevance, when not to call) appear in [Hammer](https://arxiv.org/abs/2410.04587) and the ToolACE-style datasets, but no independent ablation was found, so treat them as a cheap experiment, not a known gain.

Preference methods are weaker. [DiaTool-DPO](https://arxiv.org/pdf/2504.02882) found DPO alone degraded multi-turn tool use and recommends SFT first; one 8B run gained 17% on slot filling but lost 10% on relevance. [FinTrace](https://arxiv.org/pdf/2604.10015) saw DPO regress at Qwen3-8B. GRPO has the strongest headline in [ToolRL](https://arxiv.org/pdf/2504.13958), which reports +15% over SFT models in its abstract, but the controlled study found GRPO won only **29 of 54** cross-dataset settings, by under one point on average. No paper compares SFT, DPO and GRPO head-to-head at 2 to 3B. On the Mac, [mlx-lm-lora](https://github.com/Goekdeniz-Guelmez/mlx-lm-lora) (third-party) lists SFT, DPO and GRPO, but official mlx-lm support was not confirmed, and sources disagree on memory needs for 7B-class models (16 GB versus 32 GB). The bottleneck for Halo is sequence length, not parameter count. Each training example carries the roughly 5,800-token system prompt and tool list, so a single example runs 6k+ tokens. My estimate is that LoRA SFT on E2B with rank 8 to 16, batch size 1, gradient accumulation and checkpointing fits in 16 GB, but that is unmeasured. Loss masking on the prompt and a trimmed prefix are the two levers if memory fails. GRPO would multiply that cost by the rollouts per prompt, so it stays out of the first plan. The number of verified trajectories needed is not sourced; hundreds to low thousands is a guess to test with a learning curve.

## Inference-time fixes come before retrieval and constraints

Constrained decoding is the technique most likely to backfire here. The Constraint Tax study on Qwen2.5 and SmolLM2 models found hard answer-only schema decoding raised validity from 61.5% to 100% but cut answer accuracy from 19.7% to 11.0%, with wrong-but-valid outputs rising to 88.9% of constrained outputs ([arXiv 2605.26128](https://arxiv.org/abs/2605.26128)). Halo's E2B is already 100% schema-valid, so argument-level constraints buy almost nothing. A tool-name enum prevents only nonexistent tools, which Halo's validator already catches, and it does nothing about the 34.9% wrong-but-valid first moves. MLX itself does not enforce schemas; [LM Studio's MLX post](https://lmstudio.ai/mlx) points to Outlines, and mask costs reported in the literature disagree by about three orders of magnitude ([arXiv 2608.12574](https://arxiv.org/pdf/2608.12574) versus [arXiv 2608.03065](https://arxiv.org/pdf/2608.03065)), so any engine needs a local timing run.

Validator-guided retries are a better bet, provided they are tied to external signals. Self-refinement without a verifier can hurt small models; one code-generation table showed [Self-Refine falling from 43.8% to 38.2%](https://arxiv.org/pdf/2505.23060). An external signal, such as a validator error or a tool result, is a different case. Halo's own 11.6% announce rate is a deterministic symptom: the reply contains a described action and no tool call. A detector for that, plus one re-prompt that quotes the exact validator message, costs about one extra step on the rare turns it fires. Multi-turn prompt-based reflection is fragile, since models repeat the mistake after a failed call, and [training reflection helps](https://arxiv.org/html/2509.18847v2), so keep it to a single capped retry. Prompt format matters as much as any of this. On BFCL, [Phi-4 Mini scored 67.9% with prompt-based calling and 38.0% with native calling](https://arxiv.org/pdf/2608.22472), and [a small edit to the default system prompt moved Qwen3 multi-turn scores substantially](https://arxiv.org/pdf/2606.00135). Halo should test its native tool block against a plain-text function spec before adding few-shot examples. Each worked example likely costs 100 to 300 tokens (my estimate), and no study measured few-shot gains for 1 to 8B models.

Tool retrieval has evidence but a catch. [TinyAgent's fine-tuned DeBERTa retriever](https://arxiv.org/html/2409.00608v2) cut the tool prompt from 2,762 to 1,397 tokens while raising success from 78.89% to 80.06% at 1.1B and from 83.09% to 84.95% at 7B. That retriever was trained, and an untrained embedding retriever was not measured. Retrieval also conflicts with prefix caching: changing the tool set each turn invalidates the stable prefix. [LM Studio's engine](https://lmstudio.ai/blog/mlx-engine-agentic-workloads) checkpoints KV caches at 256-token boundaries and reports up to 2x throughput on repeated long-context agentic work (vendor claim). Halo's cached fixed prompt already gives 0.09 s to first token, so the latency case for retrieval is weak. Its real value is accuracy from fewer distractors, which needs a test. Put core tools first, retrieved tools after, and keep the core set always present. For "find X on page," a local extraction sub-call over stored page text keeps 3 to 4k tokens of page content out of the main context; [Prune4Web](https://arxiv.org/html/2511.21398v1) reports 25 to 50x candidate reduction, though that is author-reported and web-grounding specific.

## The hybrid works if privacy is enforced in code

The best-matched published design is [PAPILLON](https://arxiv.org/pdf/2410.17127), where a local model rewrites each request before a cloud model generates. Its best configuration, a local Llama-3.1-8B with cloud GPT-4o-mini, kept high response quality on **85.5%** of queries and limited privacy leakage to **7.5%** on the PUPA benchmark. The authors say a large quality gap to proprietary models remains. E2B is smaller than that 8B redactor, so leakage is likely worse, which is an inference to measure. Model-based redaction is not a guarantee, so Halo should add a deterministic layer: send structured fields only, never raw file contents, and block known sensitive patterns (names, account numbers, paths, emails) in Swift before anything leaves the device. There is also a gap in the obvious design. If DeepSeek writes a placeholder plan from the user's request, the request text itself reaches the cloud, so the sanitizer must run on the request before the planner, not only on tool outputs. Apple's public hybrid material says only that on-device is the default and that larger requests go to Private Cloud Compute ([Apple Security](https://security.apple.com/blog/private-cloud-compute/)), so Halo cannot copy a published routing policy.

For planning, the planner-executor split is the best-supported structure. [α-UMi](https://arxiv.org/html/2401.07324v2) with a 7B model reached 88.92 plan accuracy on in-domain ToolBench against 80.28 for GPT-4, and its one-stage multi-LLM ablation dropped ToolAlpaca process accuracy from 41 to 2, which shows staged training matters. The result depends on fine-tuning on each benchmark's tools, so it does not show an untuned E2B can plan. The handoff should be a typed record: goal, sanitized sub-question, placeholder keys with types, and a result schema. Tool outputs stay local. For escalation, the local signals in order of trust are validator failure after one retry, step or retry budgets, and token log-probabilities. Verbalized confidence from a 2B model is the weakest, and probes need model weights and labels. Cascade savings reported by [RouteLLM](https://arxiv.org/abs/2406.18665) (over 2x) and [FrugalGPT](https://arxiv.org/pdf/2305.05176) come from chat and classification tasks, and [AutoMix](https://arxiv.org/pdf/2310.12963) reports results that vary by version. None measures a small-model-first cascade on privacy-sensitive tool use. Halo's cost case depends on the local hit rate, which only its own exam can give.

## Ranked plan for a solo developer

Ranked by expected impact on the 86-task exam divided by effort, with the reasoning above behind each row. Effort estimates are my judgment.

| Rank | Change | Expected impact | Effort | Why this rank |
|---|---|---|---|---|
| 1 | Make the exam trustworthy: site-disjoint split, 3 to 5 runs, pass^k, state-based grading, false-success class | Enables every later decision; cuts noise from about 5 points per run | Low to medium | Without it, a 5 to 10 point gain cannot be told from noise |
| 2 | Announce and wrong-tool detector with one validator-quoting retry | Targets the 11.6% announce bucket directly; cheap per turn | Low | Deterministic signal; extends the existing validator |
| 3 | LoRA SFT on Gemma E2B from Halo's verified step-level trajectories, site-disjoint, with prompt loss-masking | Largest expected gain, most supported by literature; main risk is held-out site generalization | Medium | Data already exists; memory is the open question |
| 4 | Prompt-format test: native tool block vs plain-text spec | Possibly large; literature shows tens-of-point swings | Low | A few runs on the existing exam |
| 5 | Irrelevance and when-not-to-call examples in the SFT mix | Unknown; targets the 34.9% wrong-tool bucket | Low once step 3 exists | Weak evidence, cheap to add |
| 6 | Trained or embedding tool retrieval with an always-on core set | Accuracy gain plausible; latency gain small given caching | Medium | Conflicts with prefix cache; test after 2 to 4 |
| 7 | Cloud escalation with deterministic sanitizer and typed handoff | Depends on local hit rate and leakage; required for the hybrid | High | Privacy layer must exist before any cloud call |
| 8 | DPO after SFT | Uncertain; alone it degrades | Medium | Only after a stable SFT model exists |
| 9 | GRPO | Under one point in controlled comparison; memory heavy | High | Last; no 2B evidence |
| 10 | Hard constrained decoding of arguments | Likely negative per Constraint Tax | Medium | Skip; the model is already 100% valid |

## Conclusion

The most useful finding is that Halo's largest gap is not validity but judgment: right tool, right target, and act-versus-announce. That makes the cheap validator retry and the verified-trajectory SFT the two first moves, both built on data and signals Halo already has. The 18-point familiar-versus-new-site gap is a warning that the next gains will come from generalization, so the held-out split is the metric that matters, not the headline 48.8%. Two numbers would change this plan: an end-to-end Gemma run with retries against the 75% ChatGPT baseline, and a LoRA memory measurement on E2B with a 6k-token example. If SFT lifts new-site performance by more than about 10 points, the hybrid escalation becomes a cost decision. If it does not, the cloud partner becomes the main path for hard tasks, and the sanitizer becomes the most important component in the system.
